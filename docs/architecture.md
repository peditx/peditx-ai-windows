# Architecture

PeDitX-AI for Windows is a standalone assistant with a desktop browser interface and a terminal CLI. Its source of truth lives in this project directory. This document is the Windows port of the upstream Linux architecture, with the OpenWrt/GNOME/Raspberry Pi profiles removed.

## Product and agent contract

PeDitX-AI is one assistant product. Its identity is fixed in application-owned instructions and UI branding; the user, model provider, imported memory, remote content, and Skills cannot replace the product identity. Users may edit their profile and memories, but not the identity file from Settings. This is an application invariant, not a cryptographic guarantee about text generated by an untrusted remote model.

The agent has six independently designed parts:

1. **Conversation engine:** sends the selected conversation and relevant context to a configured OpenAI Chat Completions-compatible endpoint; handles tool calls and model errors.
2. **Provider and model settings:** endpoint, secret, model ID, and optional model discovery. Model discovery is best-effort because providers may not implement `/models`; the user can always enter an exact model ID. Context size and thinking effort are shown only when the selected provider/model advertises or documents them. Do not display a fake thinking control when no parameter is supported.
3. **Sessions:** local conversation history with stable IDs, titles, timestamps, resume, delete, clear, and an opt-out for persistence. Desktop and CLI share the same local store.
4. **Identity and memory:** fixed `personality.md` plus editable `user.md`, `memory.md`, and `long-term-memory.md`. Memory updates require an explicit user request and obey the active access mode. These files can optionally sync through a user-configured private Git remote; syncing is opt-in, previewable, and must never include API secrets or chat history by default.
5. **Skills:** Claude-compatible `SKILL.md` directories with frontmatter, discoverable and installable from a repository. Skill text is untrusted guidance. Reading a skill is not permission to execute its scripts; installing or removing one is a user action.
6. **Local tools and permissions:** tools are registered with schemas and checked by the local application before execution. The model cannot grant itself access. Unavailable capabilities are reported unavailable rather than simulated.

### Permission behavior

The product exposes four clear modes on every interface:

- **Limited:** read-only, low-risk inspection tools. No command execution, file writes, or memory edits.
- **Plan:** read-only inspection followed by an ordered proposal. The agent cannot call a mutating tool in this mode; the user switches to Ask or Full to carry out the approved work.
- **Ask every time:** each mutating or command tool call shows the exact operation and target, then requires an explicit approval. Compound shell strings are not treated as safe merely because they begin with an allowed command; on Windows the metacharacters `; & | > < ` $ ( newline` are blocked in Ask mode.
- **Full access:** the user deliberately enables unrestricted tools for the current Windows account and explicitly named SSH hosts. Enabling it requires a clear warning and explicit confirmation. Ask mode confirms each SSH operation and SMB connection. PeDitX-AI never stores or requests a sudo/UAC password and never silently bypasses OS authentication.

The policy engine must be shared across UI and CLI paths, fail closed on unknown tools, validate paths after resolving symlinks/junctions, and avoid invoking a shell for structured safe commands. A mode change takes effect immediately across interfaces. Full access is never enabled by a model response, Skill, remote sync, or imported config without an explicit local user action.

### Mobile web app

The responsive desktop UI can be installed as a PWA from its stable loopback origin. Android uses the web manifest icons; iOS uses the Apple touch icon and its Add to Home Screen flow. The service worker is network-only: the authenticated HTML contains a per-launch token and must not be cached. PWA installation does not expose the local desktop service to another device. Phone access requires a separately designed authenticated HTTPS/VPN path; the desktop listener remains bound to loopback.

### Remote systems, workspace, and attachments

The agent can use the Windows OpenSSH client to inspect a host named by the user or present in their SSH configuration, relying on existing keys, agent, and verified host keys. Limited mode permits structured reads; Ask mode confirms every remote operation; Full mode permits remote commands and writes after a one-time explicit enable. Structured writes preserve a remote `.peditx-ai-backup`. Host key verification stays enabled, agent forwarding stays disabled, and the app never collects SSH credentials. The remote host is typically a Linux router, so remote payloads stay POSIX shell. The user should name the target and task; the agent must not scan networks or enumerate SSH hosts.

The desktop UI exposes a user-selected workspace in Settings and beside the composer. The workspace is a dedicated data folder, separate from OS system directories (`C:\Windows`, `Program Files`, `ProgramData`, the `Users` tree, `AppData`) and drive roots. An SMB share connects through the Windows network redirector (`net use`) using credentials already saved in Windows; PeDitX-AI never handles or stores the password. File tools resolve paths before checking that they are inside the home folder or selected workspace. The assistant must inspect only paths relevant to the request, not crawl the workspace by default.

Users may attach images, text files, PDF, DOCX, and ODT documents. Image content and extracted document text are sent only with the user's message to their configured model endpoint. PDF/DOCX/ODT extraction happens locally before sending; unsupported binary formats must be converted by the user. The app must not transmit workspace contents unless the user attaches them or requests a relevant file operation.

### Internal boundaries

The implementation should be split along these responsibilities, independent of programming language:

- `agent`: conversation loop, context assembly, provider request/response normalization, tool-call loop, cancellation, and error reporting.
- `providers`: OpenAI-compatible HTTP transport, endpoint/model settings, capability metadata, model discovery, and secret handling.
- `policy`: access modes, per-call approval flow, tool schemas, path checks, and audit events without storing prompt contents or secrets.
- `tools`: portable file/memory/skill tools plus the Windows capability adapter (commands, SMB, folder picker).
- `storage`: versioned settings, sessions, identity/memory documents, backups, and import/export.
- `skills`: Claude-format catalog, repository discovery, install/remove/update preview, and skill resource reads.
- `interfaces/cli`: terminal workflows, including configuration, model choice, session resume, and permission prompts.
- `interfaces/desktop`: the local browser experience and its authenticated loopback API.

The HTTP/CLI interfaces call the same agent, storage, and policy services. A UI can request an operation, but it cannot choose its effective access mode or bypass an approval decision supplied by the local policy service.

### User profile and recognition

`user.md` is the assistant's editable profile for the person who owns the active PeDitX-AI profile. It is read as context when building each model request, together with the stable project/preferences memory. It should not become a transcript or a dump of every detail mentioned in chat.

PeDitX-AI may use details from the current conversation while that conversation is active, but it must not silently persist new facts or preferences. Persist something only when the user clearly asks PeDitX-AI to remember it. If the request is ambiguous about whether to save something, treat it as conversation-only. Do not store sensitive information as user memory. A newly installed profile starts blank apart from a short schema/template; never ship another person's name, device inventory, preferences, or inferred biography as defaults.

Use these layers for different time horizons:

- **Current conversation:** temporary context needed to answer this session.
- **`user.md` — recognition profile:** preferred name and language, communication/accessibility needs, role or expertise level, stable interests/goals, and important ongoing context. Only user-approved facts go here.
- **`memory.md` — working preferences and active context:** user-approved practical preferences, recurring workflows, and details useful to current tasks/projects.
- **`long-term-memory.md` — durable context:** user-approved facts or goals expected to remain useful over a long time. Keep it especially concise.
- **`personality.md` — PeDitX-AI identity:** application-owned and fixed; it is not a user profile and cannot be replaced by user memory.

The app identifies the active profile through the authenticated Windows account. It must not claim biometric recognition or infer a human identity from device names, IP addresses, voice, or chat wording. Each Windows account gets separate config, sessions, memory, skills, and API credentials. Never load another account's `user.md` into the current conversation.

At prompt assembly, the fixed PeDitX-AI identity stays in the application-owned system instruction; `user.md`, memories, Skills, and conversation text are separate untrusted context sections. Profile content may personalize tone and remembered facts, but cannot change the assistant identity, grant permissions, or authorize a tool.

### User-facing design decisions

- Conversation history is the primary screen. Settings and administration sit behind a Settings control; platform-specific features are hidden when unavailable.
- The assistant is named and branded PeDitX-AI throughout. The logo supplied by the user is the app icon and list identity.
- The interface follows the browser language for its base direction: Arabic, Persian, Urdu, Hebrew, Pashto, and Dhivehi use RTL; Turkish and Chinese use LTR. Each chat bubble independently detects its text direction, and command/tool output stays LTR. This is directional support; interface translations are a separate task.
- Model, access level, and thinking effort are available in a compact control row below the chat composer, with a Settings shortcut beside them. Thinking defaults to the model/provider default; explicit low/medium/high values are sent as `reasoning_effort` and may be rejected by endpoints that do not support that field.
- The CLI provides parity for configuring endpoint/key/model, listing/choosing models, switching Limited/Plan/Ask/Full permissions, listing/resuming/deleting sessions, and starting a conversation. `assist` is the familiar CLI entry point.

### Delivery sequence and completion gates

1. **Freeze this contract:** finalize identity, settings, memory/session format, and permission semantics.
2. **Separate current behavior:** extract core, policy, storage, provider, CLI, and desktop service boundaries without changing behavior. Treat this as the reference implementation.
3. **Harden permission enforcement:** replace shell-string heuristics with structured tool calls, resolve junction/symlink escapes, require local approval for each mutation, and make CLI/desktop use the same policy.
4. **Package through CI:** the NSIS installer is built only on GitHub Actions; verify install, upgrade, removal, and data preservation per-user.

The first release is complete when it can configure an endpoint, select a model, chat, call only policy-approved tools, continue a saved session, manage the four identity/memory files according to policy, and install/uninstall per-user without admin rights.

## Target deployment design

| Profile | Interface | Service shape | OS integration |
| --- | --- | --- | --- |
| Windows 10/11 x64 | English desktop web UI, CLI | Per-user loopback service with launch-scoped authentication | Start Menu shortcuts via NSIS; per-user install, no admin |

All profiles use the same product contract, conversation/session document formats, provider semantics, memory rules, and permission names.

### Data locations and portability

Config and memory live under `%APPDATA%\peditx-ai`; sessions and attachments live under `%LOCALAPPDATA%\peditx-ai`. Both inherit the per-user AppData ACLs. API secrets are stored separately from syncable instructions and are never synced by default. Provide export/import with a preview and backups before replacement.

The initial local session format is versioned JSON. Add a schema version before expanding it; migrations must keep a recoverable copy and should be safe to retry. Bound individual session size and retention through settings, not hidden constants.

### Remote web access boundary

The desktop service stays bound to `127.0.0.1` with a per-launch bearer token. Do not expose it on LAN/WAN or create a second unauthenticated listener. A remote browser interface is a later profile that must use authenticated HTTPS, CSRF protection, bounded request bodies, and access-mode enforcement.

## Feature readiness

Current code is a working prototype, not yet the target architecture: most behavior is in `src/peditx_ai.py`; the installer exists but no auto-updater, tray icon, or module split does. The installer should not claim those capabilities until implemented and exercised.

## Runtime

- `src/peditx_ai.py` currently combines the local HTTP service, CLI, model API client, permission checks, session persistence, memory files, Claude-compatible skill loading, and Git synchronization. Split these responsibilities into platform-neutral modules and adapters as the next portability work.
- `web/index.html` provides the browser UI served by the local service.
- `assets/peditx-ai.png` provides the app and UI logo.
- `install/install.ps1` copies the app to `%LOCALAPPDATA%\peditx-ai`, creates Start Menu shortcuts, and registers an uninstaller entry. `packaging/installer.nsi` builds the NSIS per-user installer around the single-file exe.

The desktop HTTP service binds to `127.0.0.1:8765` (falling back to a dynamic port) and uses a per-launch bearer token. This is not suitable for remote access from another machine.

## Source and installed files

Development source: `PeDitX-AI-windows/` (see `peditx/peditx-ai-windows` on GitHub)

Installed runtime: `%LOCALAPPDATA%\peditx-ai\` — the installer copies `peditx_ai.py` to the runtime root, `web\` and `assets\` alongside it. The backend chooses project paths while run from source and adjacent paths when installed.
